# 审批绑定的投递执行设计

## 背景

AI Job Search Copilot 已确定由生产 Web 运行时重建 `ai-job-search` 的领域工作流，岗位来源、匹配、简历和投递状态由应用持有，而不是在服务器运行面向开发者的仓库实例。AIHawk 展示了求职流程最终会遇到表单识别、附件上传、登录态、iframe、Shadow DOM、多步骤页面和提交结果确认等执行问题，但其默认自动投递思路与本项目的审批边界不一致。

AIHawk 调研结论固定在 2026-08-28 检查的 `feder-cr/Jobs_Applier_AI_Agent_AIHawk` `main` 提交 `79155b52faccfbd19b834680af285eac70dd2df4`：当时 README 明确说明第三方 provider plugins 已移除，仓库许可证为 AGPL-3.0。后续上游变化不自动改变本项目决策，需要重新评估。

本设计吸收这些执行问题和工作流经验，不集成 AIHawk 代码。MVP 与正式 Beta 的范围保持不变；浏览器辅助执行属于正式 Beta 之后的独立能力。

## 目标

- 为未来浏览器辅助投递定义稳定、可测试的执行 seam。
- 保持岗位发现、匹配、材料生成、审批、执行和投递状态之间的职责分离。
- 让每次外部信息写入和最终提交都绑定用户看到的确定内容。
- 在页面变化、未知字段、登录验证、重复提交或结果不确定时安全暂停。
- 让手动投递与未来浏览器执行产生一致的投递记录和投递快照。

## 非目标

- 不改变 MVP 或正式 Beta 的范围与开发顺序。
- 不在本次工作中实现投递领域代码、浏览器扩展或招聘平台 Adapter。
- 不建设批量海投、无人值守提交、验证码绕过、反检测或账号托管。
- 不承诺支持任意招聘网站，也不优先自动化 BOSS 直聘、猎聘等强登录和强风控平台。
- 不把投递执行抽象成求职以外的通用 Browser Agent 平台。

## 产品边界

MVP 与正式 Beta 使用 Manual Adapter：系统准备定制材料和投递记录，目标求职者在外部页面完成真实投递后回到产品确认。正式 Beta 之后可以逐站加入 Browser Adapter，先支持只读检查和辅助填写，再单独评估是否允许审批绑定的最终提交。

浏览器辅助执行不改变产品“不是自动投递器”的定位。它减少已经决定投递后的重复操作，不替代岗位选择、材料审核和用户最终决定。

## 模块与 seam

```text
岗位来源 / AnySearch / 公司 Watchlist
                ↓
       岗位机会与匹配评估
                ↓
        定制简历与确认答案
                ↓
           投递准备包
          ┌─────┴──────────────────────┐
          ↓                            ↓
   Manual Adapter              Browser Adapter
   用户在外部投递              只读检查与执行计划
          ↓                            ↓
   事后确认 + 可用回执           填写审批 → 填写
          │                            ↓
          │                     提交前审核快照
          │                            ↓
          │                     提交审批 → 提交
          └────────────┬───────────────┘
                       ↓
              投递执行尝试 / 投递回执
                       ↓
                投递快照与投递记录
```

服务端是投递内容、审批和业务状态的权威来源。Browser Adapter 持有招聘平台页面和登录态，只能执行服务端允许的具体动作，不能生成或修改画像事实、简历、法律答案或投递状态。

Manual Adapter 与 Browser Adapter 使这个 seam 成为真实变化点。Manual Adapter 不代表系统执行外部行动：用户先在外部页面完成投递，再以事后确认和可用回执形成执行结果。Browser Adapter 代表系统执行外部行动，因此使用行动前的填写审批与提交审批。两者都必须输出可归档的执行结果，且只有满足提交证据规则后才能推进投递状态。

## 领域对象

### 投递准备包

投递准备包针对一个来源发布版本，引用确定的简历版本、附件和全部已知表单答案。它从创建起不可变；任何材料或答案变化都会产生新版本，并使引用旧版本的待审批事项或审批失效。

### 投递执行计划

Browser Adapter 先只读检查具体页面并返回规范化字段描述。系统使用投递准备包和已验证画像证据生成投递执行计划，记录：

- 求职账户与投递记录；
- 来源发布版本和页面来源；
- 投递准备包版本；
- 页面指纹；
- 字段与已确认值的映射；
- 未解决、敏感或不支持的字段；
- 当前允许的动作；
- 计划版本和内容摘要。

页面返回的数据属于不可信职业内容，只能作为字段和页面状态数据，不能改变 Agent 指令、工具权限或审批范围。

### 投递执行尝试

Manual 渠道在用户返回产品确认外部投递后创建投递执行尝试，绑定投递准备包、投递确认、渠道和可用回执，不创建 Browser 专属的执行计划、审批或提交前审核快照。Browser 渠道的每次填写或提交创建独立投递执行尝试，绑定执行计划、对应审批和渠道。成功、失败、取消与结果未知都保留；重试创建新尝试，不能覆盖已有记录。

### 提交前审核快照

Browser Adapter 完成填写后重新读取页面，形成不可变的提交前审核快照。它固化最终字段值摘要、附件版本、页面来源和页面指纹；提交审批绑定这个快照的内容摘要。点击提交前必须再次比对，任何字段、附件、来源或页面指纹变化都会使提交审批失效。

### 投递回执与投递快照

投递回执可以是外部确认编号、明确结果页面或其他可核验结果。Browser 提交缺少可靠回执时，执行结果为“结果未知”，不能直接把投递记录推进为“已投递”。投递快照绑定投递准备包、渠道、时间、投递执行尝试、可用回执以及该渠道的提交证据：Manual 使用投递确认，Browser 使用提交审批。它继续作为真实投递的不可变证据。

## 两阶段审批生命周期

```text
只读检查页面
    ↓
生成投递执行计划
    ↓
解决未知字段
    ↓
用户审批“填写”
    ↓
按计划写入外部页面
    ↓
重新读取并核对最终页面
    ↓
形成提交前审核快照
    ↓
用户单独审批“提交”
    ↓
一次性提交
    ↓
回执 / 失败 / 结果未知
```

填写和提交是两个不同外部行动。现代页面可能在输入、失焦或切换步骤时向招聘平台传输个人信息，因此填写前也必须审批；填写审批不能延伸为提交审批。

每次审批至少绑定投递准备包版本、动作所用内容摘要、页面来源和动作类型。填写审批绑定投递执行计划，提交审批绑定提交前审核快照。两类审批都具有有限有效期，并在对应执行尝试开始时单次消费；失败、取消或重试需要新审批。页面指纹、字段、材料、答案或来源变化会使审批失效，批量或跨岗位复用审批无效。

## 字段处理规则

- 姓名、联系方式、经历和技能只能来自当前有效画像事实或已确认投递准备包。
- 工作许可、签证、sponsorship、薪资、入职时间、EEO、自我认同和法律声明必须使用用户已确认值；缺失时暂停并由用户处理。
- 模型可以在受约束步骤中建议字段映射，但不能获得提交工具，也不能创造答案。
- Browser Adapter 只能填写执行计划中列出的字段；出现额外必填字段时必须暂停。
- 文件上传只能选择投递准备包绑定的不可变简历或附件版本。

## 登录态、隐私与信任边界

- 招聘平台 Cookie、令牌、设备状态和登录会话保留在用户浏览器，不上传到服务端。
- 服务端不保存 BOSS 直聘、猎聘或其他招聘平台账号与密码。
- 服务端按渠道保存投递准备包、投递确认或审批、执行计划、脱敏执行尝试与回执以及权威业务状态；页面证据只有在独立受控存储与保留策略获批后才能保存。
- 页面 DOM、iframe、开放 Shadow DOM、脚本提示和错误信息都是不可信输入。
- 简历正文、联系方式、完整表单值、页面截图和浏览器会话信息不进入普通日志、OpenTelemetry 或 Sentry。
- 如果未来保存包含个人信息的页面证据，只能进入受控业务存储，并采用独立访问和保留策略。
- CAPTCHA、短信验证、双重验证、异常登录提示和平台风险提示必须交还用户，不允许规避。

## 失败、幂等与恢复

- 页面指纹、来源或字段发生变化：执行计划失效，重新检查页面并请求新审批。
- 未知必填字段：暂停，不猜测默认值。
- 登录失效、双重验证或 CAPTCHA：交还用户，恢复后重新验证页面状态。
- 部分填写失败：记录已完成字段和失败位置，不自动继续到提交。
- 提交前检测到相同岗位可能已经投递：阻止提交并请求用户核对。
- 提交超时或页面关闭且无可靠回执：记录结果未知，不静默重试。
- 已获得明确回执：提交审批和执行尝试完成，创建投递快照并推进投递记录。
- 取消或失败后的重试：创建新执行尝试；原尝试和审计证据保持不变。

提交动作需要业务幂等键，并在执行前后检查同一投递记录是否已经存在成功回执或结果未知尝试。幂等不能把一个不确定的远端结果误判为安全可重试。

## 分阶段路线

### MVP 与正式 Beta

- 生成定制简历和投递准备材料。
- 用户在外部页面手动填写和提交。
- 用户回到产品确认投递并形成投递快照。
- 不实现 Browser Adapter。

### 正式 Beta 之后：页面检查

- 在用户侧读取当前招聘页面和表单结构。
- 规范化字段并识别来源、页面变化和未支持控件。
- 不写入个人信息，不上传文件，不提交。

### 正式 Beta 之后：辅助填写

- 生成投递执行计划并解决未知字段。
- 用户审批填写后，按计划写入字段和上传指定附件。
- 填写完成后暂停，用户检查最终页面。

### 后续单独决策：审批绑定提交

- 只有逐站验证稳定性、合规、回执和失败恢复后，才评估由 Browser Adapter 执行最终提交。
- 即使启用，也需要独立、一次性提交审批，不开放无人值守批量投递。

## 未来验证策略

领域测试覆盖：

- Manual 投递快照使用投递确认，不要求执行计划、事前审批或提交前审核快照；
- 内容或页面变化使审批失效；
- 填写审批不能授权提交；
- 填写审批和提交审批都只能使用一次，失败或重试需要新审批；
- 提交审批绑定提交前审核快照，点击前内容变化会使其失效；
- 未知字段、结果未知和重复投递不推进为已投递；
- 重试创建新执行尝试并保留历史。

Adapter 契约测试使用本地受控页面覆盖：

- 原生表单和文件上传；
- 单层与嵌套 iframe；
- 开放 Shadow DOM；
- 多步骤表单和条件字段；
- 页面重新渲染、来源跳转和提交超时；
- 登录、双重验证和 CAPTCHA 的人工接管点。

安全测试覆盖页面提示注入、越权字段、未审批写入、PII 日志和跨来源执行。自动化 CI 不依赖真实招聘网站；每个生产招聘来源必须单独验证、监控并允许快速停用。

## AIHawk 借鉴边界

可借鉴：

- 求职画像到岗位搜索、材料定制、表单填写和提交的完整执行链路；
- 招聘页面变化、登录态、附件、动态表单和提交回执等失败场景；
- 将招聘来源差异封装在站点 Adapter 后的方向。

不复用：

- 调研快照中的 Python/Selenium 运行时和已移除的第三方 provider plugins；
- 无监督自动提交、批量海投和反检测目标；
- 由模型临场生成法律、身份或其他高后果答案；
- AGPL-3.0 代码或与本项目产品边界冲突的实现。

## 与现有决策的关系

- 延续 ADR 0001：迁移领域意图，不运行或嵌入原始仓库实例。
- 延续 ADR 0003：强登录和强自动化限制的平台使用用户侧能力，服务器不托管平台账号。
- 延续 ADR 0014：外部行动存在明确暂停点、工具白名单和终止条件。
- 延续 ADR 0025：推荐决策、投递状态和投递执行结果互不混淆。
- 延续 ADR 0026：真实投递必须保存不可变投递快照。
- 延续 ADR 0028：招聘页面是不可信职业内容，不能扩大指令或权限。
- 延续 ADR 0030：执行步骤、审批和结果进入脱敏审计轨迹，PII 不进入普通可观测系统。
