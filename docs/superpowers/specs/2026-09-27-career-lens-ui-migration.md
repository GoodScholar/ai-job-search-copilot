# 职业透镜设计向现有 Alpha UI 迁移：#66 执行补充规格

状态：设计基线与执行边界已核定。现有 [Issue #66](https://github.com/GoodScholar/ai-job-search-copilot/issues/66) 已发布、开放且标记 `ready-for-agent`，当前没有阻塞依赖；其正文是生产交付范围，本文件补充逐页设计与验收约束，不另建同义整站 Issue。24 视图静态原型于 2026-09-28 冻结 reference-112，独立 R7 评分全部 95–96、关键缺项零；生产 UI 尚未修改。

## Problem Statement

当前网站的布局与用户确认的设计图差异明显。用户需要有突出主对象、能扫描证据和下一步、同时覆盖面试后续计划的统一产品界面。只完成品牌首页或在旧文字页面外包白卡不足以满足要求；图稿、静态原型和真实产品实现的状态必须分别可核对。

## Solution

以最新 DESIGN 和权威概念图为视觉基线，将已实现的十个 Alpha 路由及四个任务视图迁入统一职业透镜体系。品牌入口使用机会→事实→决定的透镜关系；工作台、画像、目标、来源、诊断和审核各围绕自己的主对象组织。保留现有权限、真实证据、版本、表单和运行恢复行为。面试、材料等未来页面保留完整设计和对应领域 Issue，但不在视觉重构中提前实现其后台。

## User Stories

1. 作为求职者，我希望首页清楚展示从值得投的机会到面试准备的完整旅程，从而知道产品如何陪伴求职。
2. 作为求职者，我希望机会、已确认事实与决定的关系可直接看见，从而理解推荐依据。
3. 作为访问者，我希望品牌入口通向真实登录边界，从而顺利进入工作台。
4. 作为手机访问者，我希望首先看到登录面板和可用登录行动，从而无需先滚过营销内容。
5. 作为新账户用户，我希望工作台显示真实准备步骤，从而知道还需补齐哪些资料、目标和来源。
6. 作为已有资料的用户，我希望工作台优先呈现当前最重要的行动，从而继续推荐流程。
7. 作为用户，我希望可查看运行阶段和暂停状态，从而理解 AI 运行进展和控制边界。
8. 作为用户，我希望刷新后恢复已有运行与展开信息，从而不丢失任务上下文。
9. 作为用户，我希望按岗位对象浏览机会列表，从而快速比较公司、地点和岗位。
10. 作为用户，我希望并列查看岗位要求和画像证据，从而识别优势及需补充事实。
11. 作为用户，我希望收藏、忽略和重评仍紧邻对应机会，从而做出可追溯决定。
12. 作为用户，我希望查看推荐版本、历史和校准建议，从而理解判断的来源与变化。
13. 作为用户，我希望已确认事实、候选事实和冲突分区清楚，从而审核真实经历。
14. 作为用户，我希望导入、添加、纠正和拒绝事实仍可执行，从而维护可信画像。
15. 作为用户，我希望主目标、次目标和约束摘要易扫描，从而维护求职方向。
16. 作为用户，我希望来源能力、健康和未检查状态区别明确，从而判断下一步维护行动。
17. 作为用户，我希望岗位导入的输入方式、阶段和错误贴近主对象，从而完成或恢复导入。
18. 作为用户，我希望策略显示用户设置、有效值和系统硬上限，从而控制自动运行。
19. 作为用户，我希望模型诊断说明四项真实检查、影响和建议，从而恢复连接。
20. 作为用户，我希望 Inbox 和候选审核的依据、影响及行动保留，从而作出有根据的批准或拒绝。
21. 作为手机用户，我希望主要按钮、页签和图标至少有 44px 点击区域，从而可靠操作。
22. 作为键盘用户，我希望导航、页签、展开和错误恢复保持焦点可达，从而完成同样的工作。
23. 作为用户，我希望没有真实数据时看到空态，从而不会把设计样例误认为自己的岗位、经历或运行结果。
24. 作为用户，我希望未来材料、投递和面试页面遵循同一设计体系，并明确规划阶段，从而了解后续能力与当前能力的界限。

## Implementation Decisions

- 最新用户参考图决定视觉组织；PRODUCT、CONTEXT、ADR 与真实字段契约决定产品事实。生成图中误写的格式、计数、诊断名或能力不能改变领域。
- 统一冰蓝画布、白色对象、深墨蓝文字、主蓝行动与深色 AI 区；共用导航和令牌，各页保持设计图规定的不同主构图。
- A01 桌面按统一内板比例渲染，机会、事实、决定和六步旅程不得分别缩放；手机保留完整关系对象并单独组织。
- A02 手机将访问面板前置，说明文字采用正常文档流和卡片内边距，禁止负边距挤入卡片。
- 保持现有四项主导航和画像上下文入口；未来投递导航按真实能力标示，不借静态示例伪称当前可用。
- 复用现有服务器组合与视图接缝、原生 CSS、Base UI/shadcn；不复制原型的历史层叠覆盖，不为视觉迁移新增 API、持久化或领域模型。
- 推荐证据保留完整版本与原值，不从未解析内容猜测匹配百分比；真实空态、错误、阻塞和恢复均需保留。
- 当前迁移包括十路由与 Inbox、导入审核、首次旅程、推荐校准四个既有任务态。材料、投递、面试、公开分享和账户删除后台继续属于原有独立 Issue。
- 后续文本面试必须绑定本人已确认投递及不可变上下文；原答、追问和重答保持独立历史。它们是未来规格约束，本次不创建会话 API。

## Testing Decisions

- 首选现有 Playwright 用户流程接缝：`auth-workbench`、`first-recommendation-journey`、`recommendations`、`job-triage`、`workbench-inbox`、`job-targets`、`company-watchlist`、`job-imports`、`account-run-policy` 和 `model-diagnostics`。每个接缝核对用户可见结果和真实路由流转，不从静态原型推定生产功能已就绪。
- 复用已有真实 API fixture 与 E2E 流程，验证用户可见行为和服务器契约；不为颜色、CSS 类名或实现结构建立镜像测试。
- 受影响组件补充展开、页签键盘、编辑模式、焦点回归和错误恢复测试；保留所有已有领域断言与 SSR/SSE 恢复断言。
- 所有实际十路由和四个任务态以真实内容、空态及关键失败状态采集桌面/手机截图；静态原型评分不能代替生产验收。
- 同图同尺度核对布局、主视觉、字体色彩、内容组件及移动组织；不足 95 分或有关键缺项继续修正，记录具体扣分和截图版本。
- 手机核对至少 44px 命中区域、局部滚动、页面无横向溢出、安全区和底部动作无遮挡；同时检查键盘、焦点、对比度和 reduced motion。
- 定向检查、E2E、typecheck、lint、build 由单进程串行执行，保留实际命令和结果，不重复运行已有有效且未受影响的检查。

## Out of Scope

- 新材料生成/版本/导出、外部自动投递、招聘进展后台、文本面试后台、公开分享服务和完整账户删除。
- 语音/视频面试、情绪或人格推断、无依据成果、虚构背书或百分比。
- 将原型截图作为产品 UI、直接把一次性原型代码晋升为生产代码、变更现有 API 或数据 schema。
