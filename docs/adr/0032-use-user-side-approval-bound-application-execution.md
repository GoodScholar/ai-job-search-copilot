# 使用用户侧且与审批绑定的投递执行

MVP 与正式 Beta 继续由目标求职者在外部招聘页面完成投递；正式 Beta 之后如加入浏览器辅助执行，招聘平台登录态保留在用户侧，服务端按渠道保存投递准备包、投递确认或审批、执行计划、脱敏执行尝试与回执以及权威业务状态，但不保存招聘平台凭据、Cookie、令牌或浏览器会话。Browser Adapter 代表系统执行时，填写个人信息与最终提交是两个独立外部行动，必须分别绑定确定内容和页面来源获得一次性审批；页面或内容变化会使审批失效。项目只把 AIHawk 作为流程和失败场景参考，不直接集成或复制其实现，也不把批量海投、验证码绕过、反检测或服务器端招聘平台账号托管作为产品能力。

## Considered Options

- 永久保持手动投递：风险最低，但无法在产品成熟后减少重复填写成本。
- 在服务器自动化招聘平台：便于集中执行，但账号、登录态、验证码、平台条款和多租户敏感数据风险会主导系统复杂度。
- 直接集成 AIHawk：概念验证快，但会把生产边界绑定到第三方运行时、许可证和默认自动化策略。
- 用户侧审批绑定执行：需要浏览器适配和逐站验证，但能复用用户登录态，并把内容权威性、审批和审计继续留在现有产品边界内。

## Consequences

- 投递执行必须位于明确的 seam 后面，Manual Adapter 与未来 Browser Adapter 共享同一领域结果语义。
- 浏览器只能消费已验证、已审批的内容；未知必填字段、登录、双重验证、CAPTCHA、来源变化和结果不确定都会暂停或交还用户。
- 浏览器辅助执行按招聘来源逐个启用，不承诺支持任意页面，也不使用真实招聘网站作为自动化 CI 目标。
